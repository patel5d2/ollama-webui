1. The data plan, written before the measured runs

The plan below was saved as experiment/PLAN.md before any of the measurements in this report were taken. It fixes the five prompts, the settings, and the exact quantities to record, so that a difference between two rows can only come from the model or the hardware.

The five fixed prompts (prompts.json, SHA-256 recorded in every run manifest)

IDCategoryPrompt (abbreviated)What a good answer looks like
P1CybersecurityFictional phishing email demanding a password within 30 minutes; give five safe triage steps, do not visit the link, under 120 words.Ordered triage steps; never tells anyone to enter or re-enter a password.
P2Reasoning120 requests/min, +25 %, then −20 %. Final rate? Show the calculation.120 requests per minute.
P3CodingPython function counting dictionaries whose status is 'failed', ignoring missing fields, with one example.Function that does not raise KeyError; example that matches the code.

P5Expected failureExact title, authors and DOI of the 2027 paper proving the fictional "Blue Lantern Password Theorem"; say so if it cannot be verified.An explicit refusal. Any citation is a hallucination.

Fixed settings, identical in every environment

Ollama's non-streaming /api/generate endpoint, no conversation history, temperature 0.2, top_p 0.9, num_predict 192, num_ctx 2048, seed 42, think=false. Model downloads are excluded from load time.

What is measured, and how

  • Model load — wall time of one dedicated empty-prompt request, issued after the model has been unloaded.
  • Answer time — client-side wall time of the complete non-streaming request.
  • Generation speed — the server's eval_count ÷ eval_duration; this excludes prompt processing and loading.
  • Memory — /api/ps sampled after each response: resident model allocation and VRAM allocation. This is an allocation snapshot, not peak RAM.
  • Outcome — the server's done_reason, so truncation at the token limit is visible rather than silent.

What changed after the plan was written, and why

  • Jetstream2 access arrived late (Saturday 10 October), after the Mac and Colab runs were finished. The Jetstream2 runs used the unchanged run.py and prompts.json, downloaded from the project repository onto the VM; the prompt SHA-256 in the Jetstream2 manifests is identical to the earlier runs.
  • Larger models, as planned: the plan said to try a larger Qwen model on Jetstream2. Two were run, qwen3:14b and qwen3:32b, the second deliberately bigger than the 20 GiB GPU.
  • An unplanned before/after row: the first Jetstream2 runs silently used the CPU because of a permissions problem (section 10). Those numbers were kept and labelled jetstream2-cpu-fallback, so the same VM is measured with and without its GPU.
  • A fourth environment was added: the same Mac also runs Ollama natively on the Apple GPU, so CPU-only and GPU rows exist for the same machine.
  • Hugging Face model: ollama pull hf.co/... failed, so the GGUF was downloaded directly and imported under the alias qwen2.5-hf:0.5b (section 10).
  • Server-reported load time was dropped: empty-prompt load requests return done_reason=load with no load_duration field, so the measured wall time is used and the server field is left blank rather than recorded as zero.

What actually changed in the text

  • Temperature 0.1 on Docker CPU produced step 2: "Confirm the request – Ask the employee to re-enter their password for verification." In a phishing scenario that is unsafe advice, and it appeared at the low, supposedly "safe" temperature.
  • Temperature 1.2 on Docker CPU produced step 5: "Do not enter password – Avoid revealing any credentials to prevent account compromise." — the opposite, and the better answer.
  • The same temperature-0.1 request on the other three backends (Colab T4, Jetstream2 CPU, Jetstream2 A100) did not produce the password instruction. The unsafe answer is reproducible only on the backend that produced it, which is exactly why one sample proves nothing. On the A100 the two temperatures gave differently ordered but equally safe five-step lists.
  • num_predict 64 stopped mid-sentence on every backend (on the A100 at "4. Report the incident") with done_reason=length. Nothing warns the reader that the answer was cut off; only the stop reason reveals it.
Does this matter for security work? Yes, in three ways. First, low temperature buys consistency, not correctness — one sample is not evidence that either setting is safer, and the low-temperature answer here was the dangerous one. Second, any pipeline that feeds model output into a ticket or a playbook has to check done_reason, otherwise a truncated instruction looks like a complete one. Third, a model that confidently recommends re-entering a password is a reason to keep a human between the model and the analyst.

Read the load column carefully. On Colab the first real answer for each model took 37 s even though the empty-prompt load request had already returned after 65 s, because the T4 finishes warming up on the first genuine generation. On the Mac's own GPU the same model loaded in 3.3 s and the first answer was already at full speed. Jetstream2's A100 showed the same warm-up as Colab — 35 s for the first answer after the service restarted — so this is a property of the NVIDIA/CUDA start-up, not of Colab. Cold-start cost, not throughput, is where the cloud GPUs lose.
Model size on one GPU. On the A100, qwen3:14b (8877 MiB, entirely in GPU memory) generated 88.2 tokens/s. qwen3:32b needs 20033 MiB — more than the 20 GiB slice — so Ollama placed 17121 MiB on the GPU and the rest on the CPU, and speed collapsed to 11.1 tokens/s: 2.2× the parameters for 8× less speed. The limit is not "does it load" but "does it fit in VRAM".

The most important result in this table is the P2 row. llama3.2:1b answered 120 correctly on four backends and 126 on the Colab T4 with the same prompt, the same temperature, the same top_p and the same seed. Identical settings do not produce identical text across different hardware and backends, so a model that passes a test on your laptop can still fail it on a server. Jetstream2 gave the cleanest version of this result: on the same VM, with the same Ollama, model files and seed, the CPU and the A100 produced different text for 12 of 20 baseline answers. The 0.5B model's P5 failure also grouped by backend rather than by machine: both CPU backends invented a Star Wars origin, and both NVIDIA GPUs returned the identical refusal.
Size bought correctness. Only qwen3:14b and qwen3:32b answered all five prompts acceptably. Every small model failed at least one: a refusal on the security question, an unfinished calculation, or a code example that misstated its own output.

Recommendations, each backed by the numbers above

  1. Everyday work for a security analyst → a persistent GPU server such as the Jetstream2 VM, running a 14B-class model. Only the 14B and 32B models answered all five prompts acceptably, and the security question is where the small ones failed (Llama refused it on every backend). On the A100, qwen3:14b answered in a median 0.81 s at 88.2 tokens/s; the same model on the same VM's CPU took 15.8 s per answer at 4.4 tokens/s, too slow to use all day. The 14B beats the 32B: the same correct answers, 8× faster, because it fits in VRAM. Without a server allocation, the fallback is the analyst's own native GPU (87.8 tokens/s on the small model), accepting the small models' weaker answers.
  2. Sensitive or confidential data → the analyst's own machine, native install. This is not a speed argument: locally the prompt never leaves the machine. Jetstream2 is the better second choice over Colab (your own VM on university infrastructure, rather than a commercial third party), but it is still off-device. The cost of privacy is measurable: the Mac's GPU runs qwen3:1.7b at 87.8 tokens/s against 314.9 on the A100 (3.6× slower), and only the small models were tested locally. The obvious next test is whether the 9.3 GB qwen3:14b fits in the Mac's 16 GB of unified memory; it was not run here.
  3. A quick experiment that has to be finished today → Colab, unless a Jetstream2 VM is already running and verified on its GPU. Colab needs only a Google account: about two minutes of install and model pulls, then 118.8 tokens/s. Jetstream2 was faster (314.9 tokens/s) and installed in seconds, but access took days to be granted, and the first run used the CPU at 19.8 tokens/s without any error message. Against a deadline, that hidden failure costs more than the speed saves. On Colab, accept the 37 s first answer and download the evidence before the runtime ends.

10. Problems, and how they were handled

Fetch ollama-linux-amd64.tar.zst directly, install zstd, extract into /usr/local, and skip the installer's systemd and user-account steps that a Colab VM does not need. Ollama then reported {"version":"0.34.3"} (Screenshot 1). By 12 October the official installer had been fixed and worked first time on Jetstream2.

Download the GGUF with curl, record its SHA-256, and import it with a two-line Modelfile as qwen2.5-hf:0.5b. The same method is used in Colab and on Jetstream2, and all three hashes match.
3Colab refused to start the runtime: "Too many sessions" An earlier notebook still held the single free GPU session. Terminate the stale session from Manage sessions, then reconnect. Worth knowing before a demo: the free tier gives you one.
4Empty-prompt load requests returned no load_duration The server answers done_reason=load without the timing field. Report the measured wall time and leave the server field blank. An earlier CSV recorded 0 there, which wrongly implied an instant load; the field is unavailable, not zero.
5First answers on both NVIDIA GPUs looked absurdly slow (Colab 37 s, A100 35 s) while generation speed was high The empty-prompt load returns before the GPU has finished warming up, so the warm-up lands on the first real prompt. Keep the raw numbers and report medians alongside the first-answer cost, rather than quietly dropping the outlier.

11. Limits of this comparison

  • One run per prompt. These are exploratory measurements, not statistically robust benchmarks; no repeats, no error bars.
  • The Mac CPU/GPU comparison is not clean. The container had 4 CPUs, 3.83 GiB and Ollama 0.34.2; the native Mac had 12 cores, 16 GiB and 0.34.3. The GPU is not the only variable. The Jetstream2 CPU/A100 pair is the controlled one.
  • Ollama versions differ across dates: 0.34.2/0.34.3 in September, 0.40.3 on Jetstream2 in October.
  • The A100 is a 20 GiB virtual slice (GRID A100X-20C), not a whole 40 or 80 GB card; a full A100 would fit the 32B.
  • The large models were run only on Jetstream2, so the size comparison across environments is incomplete.
  • The Jetstream2 CPU fallback is not a fair CPU benchmark. Its 16 EPYC vCPUs were slower than the Mac's 4-CPU container; the cause (CPU generation, memory bandwidth, virtualisation) was not investigated.
  • Memory is an allocation snapshot from /api/ps, not peak RSS or whole-machine usage.
  • Caches were not cleared between runs, so "unloaded" does not mean "read cold from disk".
  • Answer quality was judged by reading the answers against the expectations fixed in the plan, not by a scored rubric.
